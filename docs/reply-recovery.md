# 工具回执与超时文字收尾

## 问题与范围

`chat_completion_with_tools` 原来只把工具结果追加到局部 `history`。首轮工具完成后，后续 LLM 请求被外层 deadline 取消时，父调用仍持有原始 `messages`，重试会丢失已完成的工具回执。

本修复只增加显式内存恢复状态及逐调用完成回调，不更改模型、路由、计费、重试次数、deadline 或 SSE。工具依旧按既有调度规则执行：连续只读调用并行，副作用调用串行。

## 对外接口合同

- `state = openai_client.ToolReplyState()`：一次用户回复一个实例，不跨会话共享。
- 首次工具请求传入 `chat_completion_with_tools(..., reply_state=state)`。参数可选，默认 `None`，已有调用无须修改。
- 外层 `wait_for` 完成取消之后，后续纯文本 attempt 使用 `state.recovery_messages() or original_messages`。只做文字收尾，不再提供工具或执行器。
- `recovery_messages()` 未绑定时返回 `[]`；无工具、模型直接回复或首轮 LLM 超时则返回原始输入的深拷贝；发生工具轮后返回协议完整的 assistant/tool 配对及“不重做工具”的收尾提示。
- 输出快照与原始输入、模型返回对象及工具返回对象隔离。恢复状态仅保留与历史相同的脱敏、限长序列化结果，不存真实文件，不保存未经投影的工具大对象。

`_main_reply_with_deadline` 已接入同一回复实例的恢复状态；超时后不重做工具，只使用已有回执进行文字收尾。旧配置中的首轮与重试时长、重试次数保持不变。

## 配对与取消语义

每轮在执行工具前即构建完整快照：一个 assistant 的所有 `tool_calls` 都有对应 tool 消息。参数错误、禁止调用与调用数量截断使用原有错误回执；没有返回值的槽位明确记为 `status=unknown`、`execution_status=unknown`。

内部 `_execute_tool_calls(..., on_result=None)` 新增可选同步回调，签名为 `(call_spec, result) -> None`。并行或串行调用每完成一个便立即写入对应槽位，不等整组 `gather` 返回。写入没有 `await`，在同一 event loop 内不会与其它回调或快照读取交错；此对象不提供跨线程、多请求同时写入保证。

取消发生时已完成回执保持不变；未完成槽位变成 `status=cancelled`、`execution_status=unknown`。含义是“没有拿到完成回执，副作用可能已经发生”，不是“未执行”，也不是“成功”。由于取消不等于事务回滚，即便尚未轮到的槽位也只保守记为未知，禁止自动重做。

`CancelledError` 继续向上传播。实现没有 `shield`、后台补跑、重新提交或额外任务；已有 `gather` 的取消仍传给在飞工具，串行调用直接收到取消。若工具自身抑制取消，仍沿用既有执行控制语义，不把它强行当成未执行。父调用应在取消完成后读取状态，而不是在运行中拿快照发出另一个工具请求。

## 离线验证范围

新增 `tests/test_tool_history_recovery.py`，所有 provider 请求与工具执行器均由内存替身接管，不访问网络，不生成工具文件：

1. 已完成工具后第二 LLM round 被 `wait_for` 超时取消，回执可用于纯文本收尾且执行计数仍为一次。
2. 并行一部分完成、一部分取消，后续串行调用未启动；配对完整、已完成结果保留、未知状态明确、在飞协程按原语义退出。
3. 串行工具自取消仍传播 `CancelledError`，前序回执保留。
4. 首轮超时、没有工具、模型未调用工具均保留原输入。
5. 多个已完成工具轮不会被后续超时覆盖。
6. 禁止调用和被截断调用在取消时仍有正确配对。
7. 输入与返回快照不互相污染；结果继续脱敏。
8. 不传恢复状态的旧调用成功结果和调用方式不变。

2026-10-26 本地验证：工具恢复 9 项、真实入口 deadline 6 项、延后图片交付 5 项、发送状态 4 项、发送入口集成 3 项全部通过；整体离线清单 465 项，0 失败、0 错误，9 项原条件跳过。未调用真实模型或 QQ，未部署。

## 图片取消与发送确认

在线等待生图期间若外层取消，已受保护的生成任务仍登记到后台交付集合，等待本轮文字结束后发送，不重复提交生成请求。

主回复用 `ReplyDeliveryState` 记录 pending / delivered / unconfirmed。发送调用成功返回才更新好感、续聊与消息来源消费状态；退出处理器时把已确认文本按分泡 marker 写回历史。部分失败只保留确认部分，全部未确认则不写虚构 assistant 回复。取消或缺少 ACK 不被解释为肯定未发送，因此不盲目重发。此状态用于当前进程本轮处理，不是跨进程持久化投递队列。
